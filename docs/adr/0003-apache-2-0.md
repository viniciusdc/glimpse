# 0003 — Apache-2.0, and what that requires of the capture implementation

- **Status:** ACCEPTED
- **Date:** 2026-08-25
- **Supersedes:** the licence decision in [ADR 0001](0001-rust-and-gtk4.md)

## Context

**Why this project exists, stated plainly:** Peek is a nice tool. The goal was a
similar layout and the same capability, reimplemented — not a fork, not a port,
and with no interest in carrying any of its code forward. Reading its source was
about understanding the problem it solves, which is the ordinary way to learn
from prior art.

Peek is GPL-3.0-or-later. Glimpse began by matching that licence, on the
reasoning that a project which read Peek's source to understand the problem
should take the cautious option.

That reasoning was over-cautious, and it conflated two different things:
**reading source to understand a problem**, and **copying expression**. Copyright
protects the latter. It does not protect functionality, architecture, or the idea
of a framing window whose inner rectangle is the capture region.

## Decision

**Apache-2.0.**

## Because

Glimpse contains no Peek code. It is written in Rust against GTK4, `x11rb` and
`cairo`; Peek is written in Vala against GTK3. The language difference is
evidence, not the argument — a line-by-line transliteration into Rust would still
be derivative. What clears it is that no such translation happened, which is why
the constraint below is about code that has not been written yet rather than code
that has. GTK4's removal of the window-positioning APIs is the entire subject of
[ADR 0000](0000-x11-framing-window-spike.md), and it meant the two projects could
not converge on the same expression even where they solve the same problem. Where the two projects solve the
same problem, they solve it differently:

- Peek computes its capture rect with `gdk_window_get_origin()`. Glimpse cannot;
  it goes to the X server through `x11rb` because GTK4 refuses to answer.
- Peek's recording area is a struct of four ints. Glimpse's chain is four
  distinct types precisely so the stages cannot be confused.
- Peek's frame border is on the recording view. Glimpse's is on the parent, and
  [ADR 0000](0000-x11-framing-window-spike.md) explains why that difference is
  load-bearing rather than cosmetic.

The same reasoning was applied in the sibling project Nyx, which stays Apache-2.0
by building fresh on GPUI rather than forking GPL-licensed Zed source.

## Costs accepted — the constraints this places on future work

Apache-2.0 is only defensible for as long as the following hold. They are
requirements, not aspirations:

1. **ffmpeg arguments come from ffmpeg's documentation, not from Peek's source.**
   This is the single realest risk. Capture and encoding are not yet written, and
   Peek's exact flag sequences are short, specific, and easy to reproduce from
   memory after reading them. Derive them from
   [ffmpeg-devices](https://ffmpeg.org/ffmpeg-devices.html) and
   [ffmpeg-filters](https://ffmpeg.org/ffmpeg-filters.html). Where a flag choice
   is non-obvious, cite the documentation in a comment.
2. **No Peek assets.** No icons, `.ui` files, CSS, gschema, desktop entries,
   translations or screenshots.
3. **Describe the project accurately.** Glimpse is an independent implementation
   of an idea Peek established, not "a rewrite of Peek" in the sense of derived
   code. The README and `NOTICE` say it this way deliberately.
4. **If Peek code is ever pulled in, the licence reverts to GPL-3.0-or-later.**
   That is not a disaster, only a decision — but it must be made explicitly, in a
   superseding ADR, and not discovered later.

Peek deserves the credit and gets it in [NOTICE](../../NOTICE) and the README.
Prior art is acknowledged, not laundered.

> This is engineering reasoning about copyright, not legal advice. If Glimpse is
> ever distributed somewhere the distinction carries real consequences, get an
> actual lawyer to look at it.
